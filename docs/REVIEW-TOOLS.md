# Ревью инструментов MCP: что объединить, что оптимизировать, что не трогать

Дата: 2026-10-11. Ревизия: `7615498`. Профиль индекса: `0.7.209.0`.
Повод: 47 инструментов, 4 промпта, 5 групп — проверить, нет ли дублей и балласта, не потеряв
скорость и качество разработки модов (Lua/UE4SS, Lua+DLL, BP+Loom).

**Итог одной фразой:** мёртвых инструментов нет — три с нулём вызовов добавлены в день замера;
экономию даёт не удаление инструментов, а контекст (сжатие описаний, `detail` вместо простыней) и
несколько найденных по ходу дефектов; из объединений оправданы два, и оба — с оговорками.

Полные отчёты аудита (артефакты ревью, в git не входят): `state/review/recon.md`, `live.md`,
`lua-loom.md`, `usage.md`, `verify.md`, машинные данные — `state/review/calls.json`.

## 1. Доказательная база

| Что | Как измерено | Результат |

| Точность счёта | независимый пересчёт другим методом (PowerShell, обход JSON-графа) | claude-колонка совпала **до единицы**, расхождений по 47 инструментам — 0 |

Поверхность воспроизводится скриптом `.scratch/review-measure.ts` (замер `tools/list`), счёт вызовов —
`bun run state/review/count-calls.ts`.

Ограничения: DSH-половина (5 080 вызовов) вторым методом не подтверждалась (данные в `.zstd`);
хранилища Antigravity (`.db`/`.pb`) и архивы Codex не декодированы; размеры ответов инструментов
воспроизводились лишь там, где это не требовало живого стенда. Токены — оценка диапазоном по байтам,
причём 108 012 Б — **верхняя граница**: клиенты грузят часть описаний лениво (`ToolSearch`,
`deferred_tools_delta`), поэтому счёт «на каждый запрос» справедлив для полного набора.
Счётчик вызовов не равен популярности: `ww_game_log` вызывался 532 раза и ни разу не упомянут в
памяти проекта — «нет упоминаний» ≠ «не используется».

**Корпуса покрывают клиентские вызовы, но есть второй канал — отладочные обвязки.** Часть работы идёт
не через MCP-клиент, а через самодельные скрипты (in-memory клиент `src/scripts/_h_tmp.ts`, запускаемый
как Bash-команда): новый счётчик `state/review/count-harness.ts` нашёл 88 таких команд (80 из них —
11.10, затронут 21 инструмент), и именно ими запускался цикл Loom 11.10 (`editor-build` + `cook`).
Важно: поле `session` в `state/jobs/*.json` и `state/game-activity.json` — это **pid процесса, который
запустил джоб** (`mcp-<pid>`), а не сессия клиента; поэтому `mcp-532`/`mcp-21260`/`mcp-5356`/`mcp-38876`
не доказывают клиентский вызов. Обвязки считаются только по литерально видимым командам, то есть это
нижняя граница. Отсюда вывод: «0 клиентских вызовов» ≠ «инструмент не работает и не нужен».

Единственный доказанный случай недосчёта по транскриптам: `state/loom-probe/Intermediate/Loom/types.json`
перезаписан 13:23:24 локально, а в корпусах в окне 11:23:15–11:23:40Z нет ни одного вызова — файл пишется
только внутри `ww_loom_probe`, значит один прогон прошёл вне трёх корпусов (недекодированный клиент
или скрипт вне сессии). Это исключение, а не правило: остальные расхождения объяснились обвязками.

## 2. «Что не используется совсем» — ответ

Ноль **клиентских** вызовов за всю историю ровно у трёх инструментов, и **все три добавлены 11.10.2026**,
то есть окно наблюдения — часы:

| Инструмент | Группа | Клиентских вызовов | Прогонов обвязкой | Цена в `tools/list` | Добавлен |
|---|---|---|---|---|---|
| `ww_game_control` | live | 0 | 3 команды / 3 эха | 4 254 Б | в дереве с 10.10 (существовал и прогонялся), коммит `eccda3a` 11.10 10:31 |
| `ww_click` | live | 0 | 5 команд / 4 эха | 2 439 Б | `f835a55`, 15:11 |
| `ww_loom_probe` | loom | 0 | 3 команды / 6 записей-эхо | 1 759 Б | `f835a55`, 15:11 |

Четвёртый сегодняшний инструмент — `ww_mod_state` (та же правка 15:11) — вызван и клиентом, и обвязкой
(12 прогонов), то есть новые инструменты осваиваются сразу. **Вывод: «ноль» здесь — артефакт новизны,
а не доказательство ненужности; на этих данных упразднять нельзя.** Повторный прогон `count-calls.ts`
через 1–2 недели даст настоящий сигнал. Вместе эти три стоят 8 452 Б (7,8 % списка) — это цена
ожидания, а не аргумент.

Формулировка про `ww_loom_probe` должна быть точной: «им не пользовался ни один MCP-клиент, потому что
ни одному клиенту он не был доступен» (сервер сессии старше файла инструмента), а не «ни разу не
вызывался» — через обвязку он прогнан 3 раза (12:43:30–46 локально), что совпадает с mtime
`state/loom-probe/Probe.uproject` 12:43:31. Практический вывод: пока сервер сессии не перезапущен,
новый инструмент можно прогнать обвязкой `createServer` + `InMemoryTransport` — именно так им и
пользовались.

Содержательный сигнал — редко используемые, существующие неделями (1–9 вызовов):

## 3. Оптимизации без изменения состава инструментов

### 3.1 `version` в схемах: 36 × 197 Б = 7 092 Б
`version: versionParam` встречается в `src/server.ts` **36 раз** (проверено `grep`); вклад блока —
197 Б на инструмент (`ww_game_status` 282 Б со схемой из одного `version` против 85 Б у
`ww_index_release` без параметров). Сжатие описания до строки вида «Профиль индекса (версия игры)»
(≈53 Б) экономит ≈3,6 КБ без изменения поведения. Первоначальная оценка в 8,4 КБ была завышена в
1,7 раза, а `version` у `ww_loom_new_mod` — вообще `Version` плагина, не профиль.

### 3.2 `ww_index_status`: 4,9 КБ вывода там, где нужны 3 строки
Проверено живым вызовом: ответ — 91 строка `meta_*` (пути скретч-проектов, sha256, счётчики
сайдкара), а промптам нужны `game_version`, `index_revision`, `fingerprint`. Вызывается первым шагом
в трёх промптах, 57 вызовов в 51 сессии — за историю это ≈250 КБ контекста. Решение: `detail:
'summary' | 'full'` (по умолчанию `summary`). Тем же вызовом поглощается `ww_index_release`
(`action: 'status' | 'release'`, −638 Б, всего 3 вызова за историю).

### 3.3 `ww_loom_install`: 4 767 Б описания — самый длинный текст каталога
Проза дублирует `ww_loom_build`, `ww_loom_validate`, `ww_game_process` и `docs/TOOLS.md:203`.
Оставить контракт (`action*`, коды `game_running`/`ready_to_install`/`already_installed`), прозу убрать:
≈ −2,5 КБ. Топ-3 дорогих объекта: `ww_loom_install` 7 996 Б, `ww_call` 4 270 Б, `ww_game_control` 4 254 Б.

## 4. Объединения: что стоит и что не стоит

### Стоит (с оговорками)

**4.1 `ww_find_symbol` + `ww_search_members` → `scope: 'symbols' | 'members' | 'both'`.** −1 421 Б,
снимается вопрос «какой из двух звать» (у них одинаковый первый аргумент). Уникальна только ветка
полей: `properties` не входит в `symbols_fts` (`src/schema.ts:156-167`), метод-ветка уже перекрыта
LIKE-веткой `find-symbol` (`src/tools/find-symbol.ts:76-85`).
*Оговорка верификатора:* LIKE-ветка получает только остаток бюджета (`rest = fetchLimit − ftsRows`),
поэтому без отдельного бюджета для секции `members` метод, который сегодня находит `search_members`,
после слияния может не найтись. Схему надо дополнить правилом деления `limit` и подсчёта `total_found`.

**4.2 `ww_get_type` + `ww_get_function` → `ww_get_reflection(path, section: 'auto' | 'type' | 'function')`.**
−2 682 Б; `section='auto'` решает по `obj.kind`, ветки отказов сохраняются.
*Оговорка:* это самые горячие инструменты группы (795 + 334 вызова), а экономия раундов мала —
во всём корпусе всего 32 промаха по виду пути (`not_a_type` 7 + `not_a_function` 25). Выгода здесь —
контекст, а не скорость; правка затрагивает 5 описаний и 5 мест промптов, поэтому — отдельным решением.

### Не стоит (проверено и опровергнуто)

- **`ww_lua_api` → группа `lua`.** Опровергнуто: `docs/TOOLS.md:10-14` прямо обосновывает его в
  `recon` для Loom-режима, а Lua там пишут через `ww_game_eval` — **самый вызываемый инструмент
  каталога (2 602)**. Экономия 1 231 Б достаётся ровно тем, кто потеряет справочник. Оставить в `recon`.
- **Слияние `ww_game_status` и `ww_game_process action=status`.** Дублируется код, а не инструмент:
  слияние экономит 708 Б и теряет `readOnlyHint` на префлайте, различение `bridge_not_installed` /
  `game_not_running` и `last_log_error` в ветке «игра закрыта». Правильная правка — общий хелпер
  (см. дефект № 4), а не новый `action`.
- **`ww_loom_job action=list|status|cancel`.** Опровергнуто как самосогласованное: если у владельцев
  остаётся `action=status`, дублирование не исчезает, а инструментов становится 48; если убрать —
  теряется разбор `report.json` (`src/tools/loom-build.ts:308,453`) и проверок пака
  (`src/tools/loom-install.ts:560,579`). Нужен общий рендер job-статуса **без** нового инструмента.
- **Слияния `ww_game_eval` / `ww_call` / `ww_trace_calls`, `ww_screenshot` + `ww_click`,
  `ww_find_asset` + `ww_extract_asset`.** Роли разные (работа без индекса, проверка арности до вызова,
  причинность вызовов; чтение/запись; поиск/песочница записи), схемы с взаимоисключающими `required`
  вышли бы хуже нынешних. Оставить как есть.
- **Удаление «нулевых» по неиспользованию.** См. п. 2 — данные этого не позволяют.

## 5. Два пайплайна не страдают

Все шаги проверены по коду, а не по документации:

- **A. Lua:** `ww_scaffold_mod` → `ww_generate_hook` → `ww_deploy_mod` (горячая Lua) →
  `ww_game_log`/`ww_game_eval` → `ww_validate_mod` → `ww_package_mod` → `ww_install_mod`.
- **B. Lua+DLL:** `restart_required` (`src/tools/deploy-mod.ts:168`), `dll_only` и `dll_missing`
  (`src/tools/install-mod.ts:193-194`), проверка символов UE4SS (`src/tools/validate-mod.ts:534`).
- **C. Loom/BP:** `ww_loom_status` → `ww_lift` → `ww_event_surface` → `ww_get_function` (`loom_call`) →
  `ww_loom_new_mod` → `ww_loom_validate` → `ww_loom_build` → `ww_loom_install` →
  `ww_game_log source=modlog`. `ww_loom_probe` в пайплайне не участвует — его отсутствие в живой
  сессии пайплайн не ломает.

Ни одно из принятых предложений не убирает инструмент, кроме поглощения `ww_index_release`
(3 вызова за историю, доступ сохраняется как `action='release'`). Объединения из п. 4 сокращают
контекст, а не число шагов.

## 6. Предлагаемый порядок внедрения

**Шаг 1 — без изменения состава и поведения (≈10 КБ контекста, риск низкий):**
слим блока `version`; `ww_index_status` с `detail` + поглощение `ww_index_release`; сжатие описания
`ww_loom_install`; починка смоука (пропущенный `call()` = ошибка); актуализация счётчиков в доках.

**Шаг 2 — найденные дефекты (поведение):** таймаут cook-джоба; масштаб и нативные размеры в
`ww_screenshot`; `limit` в списке таблиц; один `findGameProcess` на вызов; `settle_ms` по аптайму
моста; фильтры у `ww_loom_validate`.

**Шаг 3 — объединения (средний риск, отдельное решение):** `find_symbol` + `search_members`,
затем `get_type` + `get_function` — каждое с калибровкой схемы по оговоркам п. 4.

После каждого шага: `bun run typecheck`, `bun run doctor`, `bun run smoke`; отдельно — замер
`tools/list` до/после (`.scratch/review-measure.ts`), чтобы выигрыш был измерен, а не заявлен.
