# План правок инструментов по фидбеку сессии

Рабочий документ, не часть публичной доки. Источник — отчёт по сессии про спавн хвостиков
и масштаб карточки. Ниже только то, с чем согласен; несогласное собрано в конце с причиной.

## Что проверено в коде до планирования

| Утверждение из фидбека | Проверка |
|---|---|
| `TEnumAsByte` виден как `byte` | подтверждено: все 935 `ByteProperty` в индексе имеют `type_name='byte'`, `UMG.ScaleBox.Stretch` в том числе; при этом `Slate.EStretch` с девятью значениями в `enum_values` лежит |
| валидатор не знает CDO | подтверждено: `parsers/object-dump.ts:103,377` выбрасывает `Default__*` намеренно (`counters.cdoSkipped`), в индексе осталось 24 записи из 6132 в дампе |
| `ww_ui_tree` берёт `FindFirstOf` | подтверждено: `tools/ui-tree.ts` собирает чанк только из `FindFirstOf([[root]])`, адресации инстанса и геометрии нет |
| трейс блокирующий и бедный | подтверждено: `tools/trace-calls.ts` = start → `setTimeout(seconds)` → stop в одном вызове; коллбэк объявлен как `(context, a1, a2)`, в сэмпл идут только `self` и `tostring(a1)`, потолок 20 сэмплов, времени нет |
| нет аналога `ww.hook` для подписок | подтверждено: в `data/lib/ww/` лежат `hook/log/obj/poll`, `watch` нет |
| нет установки релиза | подтверждено: `mods.txt` умеет править только CLI-скрипт `scripts/deploy-bridge.ts`, инструмента нет; читалка порядка загрузки (`utils/ue4ss-mods.ts`) уже есть |
| xref возможен | подтверждено: сайдкар уже тянет CUE4Parse 1.2.2, в сборке есть `CUE4Parse.UE4.Kismet`, `ScriptBytecode`, `EX_FinalFunction`, `EX_VirtualFunction`, `EX_LocalFinalFunction` — байткод cooked-BP читается тем же путём, что таблицы |

## Порядок работ

| Очередь | Пункты | Почему так |
|---|---|---|
| 1 | B (enum'ы), C (CDO) | часы работы, снимают по целой неудачной попытке каждая |
| 2 | A (трейс) | самый дорогой пункт фидбека из дешёвых в реализации |
| 3 | D (ui_tree), E (ww.watch) | закрывают весь UI-цикл |
| 4 | I (ww_call), F (ww_install_mod) | новые инструменты, задевают границы сервера |
| 5 | G (статический xref) | отдельная большая работа на сайдкаре и схеме индекса |

## A. `ww_trace_calls`: неблокирующий, с полными аргументами и временем

**Проблема.** Один вызов держит окно 10–15 с, параллельно ничего не сделать, а в выдаче —
только счётчик, `self` и `tostring(arg1)`. Вопрос «агенты создаются до или после обработчика
клика» такой выдачей не закрывается.

**Правка.**
1. Аргумент `action: 'start' | 'read' | 'stop'`. Одноразовый режим с `seconds` оставить: для
   «вызывается ли вообще» он удобнее. Состояние уже лежит в `_G.__WW_TRACE` и переживает
   вызовы — нужна только выдача без ожидания и `session_id` в ответе, чтобы `read` не забрал
   чужую сессию.
2. Коллбэк генерировать по индексу, а не фиксированным `(context, a1, a2)`: арность и имена
   параметров берутся из `function_params` — ровно так, как это уже делает `ww_generate_hook`.
   В сэмпл идут все параметры по именам.
3. Сериализация значений — вынести рекурсивный `serialize` из `bridge/WWBridge/Scripts/main.lua`
   в `data/lib/ww/dump.lua` и вызывать из чанка через `require` (мост уже расширяет `package.path`).
   Глубина 2, обрезка строк, `GetFullName()` для userdata.
4. В каждой записи: `t_ms` от старта окна (`os.clock()`), порядковый номер, путь. Это и даёт
   привязку «до клика / после клика» без второго эксперимента.
5. Защита: кольцевой буфер (по умолчанию 50, максимум 200) и авто-деградация в режим счётчика,
   если частота выше порога — сериализация в горячем хуке съедает кадр.

**Файлы.** `tools/trace-calls.ts`, `server.ts` (схема и описание), `data/lib/ww/dump.lua`,
`bridge/WWBridge/Scripts/main.lua`, `docs/TOOLS.md`.

**Риск.** Захват аргументов на часто вызываемой функции роняет FPS вплоть до вылета — отсюда
пункт 5 и явное предупреждение в описании инструмента.

## B. `type_info` резолвит enum'ы

**Проблема.** Поле `ScaleBox.Stretch` в выдаче — `byte`, значения `EStretch` приходится
доставать отдельным запросом, и грабля «ScaleBox молча срезает масштаб >1» всплывает после
неудачи, а не до.

**Правка.**
1. `scripts/index-reflection.ts:449` — `fillFromUsmap` дописывает тип, только когда его нет.
   Разрешить перезапись для `prop_kind='ByteProperty'`: `usmapTypeToString` на `USMAP_T.Enum`
   отдаёт имя енума, `type_source` становится `usmap`. Если usmap промолчал — остаётся `byte`.
2. `tools/get-type.ts` и `tools/get-function.ts`: если `type_name` находится в `objects` как
   `kind='Enum'`, добавлять `enum_path`, а для енумов до 16 значений печатать их прямо в строке
   поля (`None=0, Fill=1, ScaleToFit=2, …`). Для длинных — подсказка `ww_get_type <enum>`.
3. Схема не меняется, но правка индексатора требует пересборки: `ww_index_release`,
   затем `bun run setup --force`.

**Файлы.** `scripts/index-reflection.ts`, `tools/get-type.ts`, `tools/get-function.ts`.

## C. Валидатор понимает CDO-пути

**Проблема.** `StaticFindObject("/Script/Engine.Default__Prototype_Agent")` — рабочий вызов,
но `ww_validate_mod` даёт ошибку, и пути приходится прятать в переменные.

**Правка.** Синтетический резолвер в `tools/common.ts`: если последний сегмент начинается с
`Default__`, снять префикс, найти класс, собрать каноническую форму CDO из пакета класса и его
имени (`/Script/UMG.Default__ScaleBox`, `/Game/Path/BP_X.Default__BP_X_C`). Вернуть hit с
пометкой `is_cdo`, чтобы `isHookable` не пропустил его в хуковые проверки. Использовать в
`checkObjectPath` (`tools/validate-mod.ts:178`) и в `ww_verify_hook`.

Альтернатива — индексировать CDO отдельным `kind` (6132 строки, копейки по размеру): тогда
работают и `suggestSimilar`, и live-проба. Дороже на один прогон сборки; делать, если
понадобится поиск по CDO, а не только валидация. Рекомендация — сначала резолвер.

**Файлы.** `tools/common.ts`, `tools/validate-mod.ts`, `tools/verify-hook.ts`.

## D. `ww_ui_tree`: адресация инстанса и размеры

**Проблема.** `FindFirstOf(root)` не даёт выбрать конкретную карточку (тестовую против
настоящей), а факта «масштаб применился» в дереве нет — он проверяется скриншотами.

**Правка.**
1. Выбор корня: к `root` добавить `object_path` (полное имя из `GetFullName`, ищется через
   `StaticFindObject`) и `index` (`FindAllOf` + номер). В шапке ответа печатать полное имя
   выбранного объекта и число кандидатов — тогда «моя или игровая» видно сразу.
2. Размеры: в `describe()` добавить `size=WxH` и `pos=X,Y`. Путь получения — `GetCachedGeometry`
   и `USlateBlueprintLibrary::GetLocalSize/GetAbsolutePosition`; доступность из UE4SS Lua
   сначала проверить отдельным спайком через `ww_game_eval` на одном виджете, по одному вызову
   за раз, и только потом вшивать в чанк. Если не поднимется — падать молча в `pcall`, как
   остальные поля `describe()`.
3. Фильтр `match_name` по имени виджета, чтобы дерево глубиной 20 не заливало ответ.

**Файлы.** `tools/ui-tree.ts`, `server.ts`.

## E. `ww.watch`: подписка на создание объектов, переживающая dev-перезагрузку

**Проблема.** `NotifyOnNewObject` после горячей перезагрузки мёртв (Lua-ref глушится мостом),
а аналога `ww.hook`, который дорегистрирует хуки, для подписок нет. Отсюда цикл «хук не
сработал → почему → а он мёртвый после reload».

**Правка.** `data/lib/ww/watch.lua` по образцу `hook.lua` и `poll.lua`: реестр в
`_G.__WW_WATCH_STATE`, одна живая подписка `NotifyOnNewObject` на класс на всю сессию, счётчик
поколений мода отсекает коллбэки прошлой загрузки (снять подписку нечем — диспетчер остаётся,
обработчик отключается по `gen`). API: `watch.for_mod(name).on(class, fn)`.

Довесок: запись в `data/lua-api.yaml` про эту граблю и предупреждение в `ww_validate_mod`, если
мод зовёт `NotifyOnNewObject` напрямую — по образцу предупреждения про `RegisterHook` против
`WWRegisterHook` в `tools/deploy-mod.ts:26`. Вендоринг в релиз подхватится сам: `ww_package_mod`
тянет всю `data/lib/ww/`.

**Файлы.** `data/lib/ww/watch.lua`, `data/lua-api.yaml`, `tools/validate-mod.ts`,
`data/templates/*.lua` (пример использования).

## F. `ww_install_mod`

**Проблема.** Установка релиза (распаковка в `ue4ss/Mods`, строка в `mods.txt`, бэкап прошлой
версии) делается руками на каждый релиз.

**Правка.** Инструмент поверх готового `utils/ue4ss-mods.ts`: вход `mod_root` или `zip`,
шаги — бэкап прошлой версии в `state/backup/<Name>-<ts>`, копирование/распаковка в
`<ue4ssDir>/Mods/<Name>`, идемпотентная правка `mods.txt` (логика `enableInModsTxt` уже
написана в `scripts/deploy-bridge.ts` — вынести в утилиту и переиспользовать), в ответе —
что изменилось. Без `force: true` отказываться перетирать каталог, не похожий на наш мод.

**Граница.** `docs/ARCHITECTURE.md` в разделе «Границы» утверждает, что сервер пишет только в
песочницу, и единственное исключение — `ww_extract_asset`. Этот инструмент правило меняет:
обновить раздел и записать точную границу — только `<ue4ssDir>/Mods/<Name>` и `mods.txt`.

**Файлы.** `tools/install-mod.ts`, `utils/ue4ss-mods.ts`, `scripts/deploy-bridge.ts`,
`server.ts`, `docs/ARCHITECTURE.md`, `docs/TOOLS.md`.

## G. Статический xref: кто вызывает функцию

**Проблема.** Половина сессии ушла на «где игра создаёт хвостиков». Ответ собирался grep'ом по
`NameMap` из вынутых `.uasset` и живыми хуками-зондами.

**Правка, поэтапно.**
1. Дешёвый предшественник: обратные ссылки на уровне ассетов. Сайдкар проходит по пакетам и
   пишет import-таблицы, из них строится «какие ассеты ссылаются на X». Закрывает вопросы
   вида «кто вообще упоминает `EmbarkBoatWhiskerGroup`».
2. Байткод: команда `xref` в сайдкаре — для каждой UFunction cooked-BP разобрать
   `ScriptBytecode` и собрать вызовы (`EX_FinalFunction`, `EX_VirtualFunction`, `EX_CallMath`)
   и обращения к свойствам.
3. Схема: таблица `calls(caller_path, callee_name, callee_path, kind, count)` с индексом по
   `callee_name`; `INDEX_SCHEMA_VERSION` поднять.
4. Инструменты: `ww_find_callers(path)` — обратный xref, и `ww_get_bytecode(function_path)` —
   линейный дизасм тела функции.

**Файлы.** `sidecar/WwParse/Program.cs`, `scripts/index-gamedata.ts`, `src/schema.ts`,
`tools/find-callers.ts`, `tools/get-bytecode.ts`.

**Цена.** Самая большая из списка, несколько дней. Делать после остального; этап 1 может уехать
раньше, он не трогает схему рефлексии.

## H. Пункт про дамп BP-графа — переформулировать, а не реализовывать

Узлы и пины (`UEdGraph`) — редакторские данные, в cooked-сборке их нет. Дампить нечего: в паке
лежит только скомпилированный байткод. Эквивалент запроса — дизасм из пункта G.

**Правка.** Строка в `docs/TOOLS.md` рядом с разведкой API: графа нет, есть байткод, — чтобы
следующая сессия не искала несуществующее.

## I. Вместо `ww_trigger` — `ww_call`

**Проблема (согласен).** Чтобы воспроизвести окно Gift Supplies, пришлось собирать виджет,
руками сбрасывать поля структуры и программно звать обработчик. Повторяемого способа нет.

**Решение другое.** Словарь игровых событий («уплатить налог», «открыть вью дока») придётся
вести руками, и он протухнет на первом же патче. Обобщённая форма: `ww_call` — вызвать UFunction
по индексному пути на найденном объекте с аргументами. Сигнатура известна из `function_params`,
значит сервер проверяет арность и типы до вызова, собирает чанк, возвращает результат и
out-параметры. Этим покрываются и «нажать кнопку dev-вью», и «уплатить налог».

Конкретные рецепты (какую функцию дёрнуть для какого окна) — это знание об игре, ему место в
памяти через `ww_memory_add`, а не в коде сервера.

**Риск.** Вызов произвольной UFunction в игровом потоке роняет игру так же, как `ww_game_eval`:
нативный access violation `pcall` не ловит. В описании — та же формулировка про один вызов за раз.

**Файлы.** `tools/call-function.ts`, `server.ts`, `docs/TOOLS.md`.

## Не делаем

**Поиск нативных C++→C++ call-site'ов.** Данных нет в принципе: UE4SS отдаёт рефлексию, а не
дизассемблер, и без символов это отдельный реверс-инструментарий, а не правка MCP. Вместо
инструмента — абзац в `docs/TOOLS.md` про то, что делать, когда трейс даёт ноль: вешать хук на
ближайшую `BlueprintCallable`-границу, искать входы через xref (G), ловить результат через
подписку на создание объектов (E).

**`ww_trigger` со списком игровых событий.** Заменён на `ww_call` — см. I.

**Полный дамп BP-графа.** Невозможен на cooked-сборке — см. H.
