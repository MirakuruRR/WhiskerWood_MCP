# Отдать свои записи в общую базу

Своё — это записи с `origin='local'`: всё, что человек накопил после последнего
`memory:sync`. `bun run memory:export --local-only` вливает их в сид, не трогая чужие
строки, так что diff пулл-реквеста состоит только из добавлений. Устройство мёржа —
`docs/MEMORY.md`.

## Как вести себя

- Пуш и пулл-реквест публичны и необратимы. До фазы 5 ничего не уходит наружу; перед ней
  покажи, что уедет, и дождись одного явного «да».
- В коммит идут только `data/memory-seed.jsonl` и, если правился, `data/memory-seed.exclude.txt`.
  Чужие незакоммиченные изменения в рабочем дереве не трогай и не коммить.
- `bun run memory:sync` после экспорта на ветке PR **не запускай**: он усыновит записи как
  `seed`, и если PR придётся пересобрать, повторный экспорт их уже не увидит. Записи
  станут `seed` сами — на первом sync после мёржа PR.

## Фаза 1. Исходное состояние

```bash
git status --porcelain data/memory-seed.jsonl data/memory-seed.exclude.txt
git remote -v
gh --version
```

- Файлы сида грязные → остановись и спроси, что это за правки: поверх них экспорт
  смешает чужое со своим.
- Апстрим — remote `upstream`, если он есть (клон из форка), иначе `origin`. Дальше —
  `<up>`.
- `gh` нет — не страшно, в фазе 5 есть путь без него.

## Фаза 2. Ветка от свежего апстрима

```bash
git fetch <up>
git switch -c memory/<YYYYMMDD>-<git user.name> <up>/main
bun run memory:sync
```

Ветка строго от `<up>/main`, а не от локального `main`: сид в ней должен быть ровно
апстримным, иначе в diff попадут чужие незапушенные коммиты. `memory:sync` здесь нужен,
чтобы подтянуть свежие записи апстрима и не отдать как «своё» то, что там уже есть.
Конфликты sync на экспорт не влияют — упомяни их и иди дальше.

## Фаза 3. Экспорт и автоматические проверки

```bash
bun run memory:export --local-only
git diff --numstat data/memory-seed.jsonl
```

- «влито в общую базу: +0» → отдавать нечего, удали ветку, вернись на прежнюю, скажи об этом.
- В `numstat` удалений больше нуля → экспорт переписал сид, а не влил в него (старая
  версия скрипта или порча файла). `git checkout -- data/memory-seed.jsonl`, стоп,
  разбирайся с причиной. Такой файл в PR нести нельзя.
- «id занят другой записью общей базы» → эти записи не уедут; перечисли их человеку,
  дальше решать ему (обычно — пересоздать запись через `ww_memory_add`, получив новый id).

Санитайзер экспорта ловит пути из конфига и `C:\Users\<имя>`, но не всё. Проверь
добавленные строки на остатки:

```bash
git diff -U0 data/memory-seed.jsonl | grep '^+{' | grep -noE '.{0,30}(\b[A-Za-z]:[\\/]|/home/|/Users/|@[a-z0-9-]+\.[a-z]{2,}).{0,40}'
```

Не утечки: пути разработчиков игры из PDB и логов (`E:\projects\arco\...`), рассуждения
вида «d:/ vs D:/». Путь в Steam-библиотеку (`workshop`, `common`) раскладку дисков выдаёт,
но безобиден — покажи и предложи заменить. Всё остальное найденное покажи человеку.

## Фаза 4. Показать, что уедет

Из добавленных строк (`git diff -U0 ... | grep '^+{'`) составь список: `public_id`,
категория, `summary`. Записей много — сгруппируй по `mod_name` и категории, но каждую
строку покажи. Отдельно выдели:

- записи, где санитайзер заменил пути (он их перечислил в выводе экспорта);
- `category=preference` — это обычно личные вкусы, а не знание об игре;
- `mod_name`, которого нет в публичных модах, — может быть приватный проект;
- `status=invalidated` — уедут с причиной, это нормально, но стоит знать.

Спроси: отдать всё, или какие-то исключить? Исключённые — строкой `<public_id> <причина>`
в `data/memory-seed.exclude.txt` (причину пиши нейтрально: файл уедет в PR), затем
`git checkout -- data/memory-seed.jsonl` и снова фаза 3.

## Фаза 5. Коммит, пуш, пулл-реквест

После явного согласия:

```bash
git add data/memory-seed.jsonl data/memory-seed.exclude.txt
git commit -m "память: +<N> записей (<git user.name>)"
git push -u origin <ветка>
```

Пуш отклонён по правам (403, `Permission denied`) — у человека нет доступа к репозиторию,
нужен форк:

- с `gh`: `gh repo fork --remote` (переименует `origin` в `upstream` и добавит форк как
  `origin`), затем снова `git push -u origin <ветка>`;
- без `gh`: попроси человека нажать Fork на странице репозитория и дать ссылку на форк,
  затем `git remote rename origin upstream`, `git remote add origin <форк>`, пуш.

Пулл-реквест в `<up>`, база `main`:

- с `gh`: `gh pr create --repo <owner/repo апстрима> --base main --head <владелец форка>:<ветка>`
  (для мейнтейнера `--head <ветка>`), в описании — число записей и разбивка по модам и
  категориям из фазы 4;
- без `gh`: дай человеку ссылку, которую напечатал `git push`, или
  `https://github.com/<owner/repo апстрима>/compare/main...<владелец форка>:<ветка>?expand=1`.

## Фаза 6. После

Верни человека на прежнюю ветку. Скажи, что дальше:

- **Пока PR открыт**, апстрим может уйти вперёд и сид в PR начнёт конфликтовать. Строки
  руками не правят: `git rebase <up>/main`, на конфликте
  `git checkout <up>/main -- data/memory-seed.jsonl`, `bun run memory:export --local-only`,
  `git add`, `git rebase --continue`, `git push --force-with-lease`. Экспорт идемпотентен
  и пересоберёт файл заново.
- **После мёржа**: `git switch main`, `git pull`, `bun run memory:sync` — записи совпадут
  с сидом дословно и станут `seed`, следующий экспорт их уже не повторит.
