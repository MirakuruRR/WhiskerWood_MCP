# BannerlordSage — архитектурный разбор

Дата анализа: 2026-08-27
Ревизия: `7708544` (ветка `main`)
Объём кода: ~14 000 строк TypeScript (`src/`) + ~500 строк C# (`tools/BannerlordSage.CSharpIndexer`)
Стек: Bun + TypeScript, `@modelcontextprotocol/sdk` 1.26.0, Zod 4.3.6, `bun:sqlite`, ILSpyCmd, Roslyn (.NET 8), ripgrep

---

## 1. Общая форма системы

Это **offline-first read-only MCP-сервер поверх предвычисленного локального индекса**. Сетевых зависимостей во время работы нет вообще: всё, что отдаётся модели, приходит из SQLite и с диска.

Система чётко разделена на два независимых контура:

```
┌─── WRITE PATH (batch, редко, минуты-часы) ────────────────────────┐
│  bun run setup                                                    │
│    ├─ обнаружение игры + детект версии (Version.xml/SubModule.xml)│
│    ├─ ILSpyCmd: DLL → .cs           (параллельно, N джобов)       │
│    ├─ копирование ModuleData/Languages XML                        │
│    ├─ Roslyn sidecar: .cs → AST-дамп JSON                         │
│    ├─ index-csharp / index-xml / index-gameplay → SQLite          │
│    └─ атомарная публикация профиля + profile.json (маркер)        │
└───────────────────────────────────────────────────────────────────┘
                              ↓  dist/games/<profileId>/
┌─── READ PATH (интерактивно, миллисекунды) ────────────────────────┐
│  MCP stdio server → 29/30 инструментов → SQLite (readonly) + rg   │
└───────────────────────────────────────────────────────────────────┘
```

Это по сути **CQRS с материализованными проекциями**: тяжёлая денормализация делается один раз в `scripts/index-*.ts`, а инструменты в `tools/` выполняют только дешёвые точечные чтения. Для задачи «дать LLM быстрый доступ к 700 МБ декомпилированного кода» это правильная базовая ставка.

## 2. Основные архитектурные методы

### 2.1. Индекс вместо grep-по-требованию (index-first retrieval)

**Где:** `scripts/index-csharp.ts`, `scripts/index-xml.ts`, `scripts/index-bannerlord-gameplay.ts`

Вместо того чтобы отдавать агенту сырую файловую систему, репозиторий строит SQLite-индекс: `csharp_types`, `csharp_methods`, `xml_entities`, `localization_entries` + FTS5-таблицы. Модель получает `read_csharp_type("MobileParty")` → мгновенный прыжок к диапазону строк, а не `grep -r class MobileParty`.

**Оценка: современно и эффективно.** Это ровно тот сдвиг, который индустрия сделала в 2025–2026: «code intelligence как инструмент» побеждает «файловая система как инструмент». Экономит и латентность, и контекст.

### 2.2. Полиглотный конвейер с sidecar-процессами

**Где:** `scripts/index-csharp.ts:324-416` (Roslyn), `tools/search-source.ts:29` (ripgrep), `utils/bannerlord-setup.ts` (ILSpyCmd)

Bun/TS выступает оркестратором, а тяжёлая работа делегируется специализированным процессам:

| Задача | Инструмент | Обмен |
|---|---|---|
| Декомпиляция | ILSpyCmd (.NET) | файлы на диске |
| Парсинг C# | Roslyn sidecar (net8.0) | JSON-дамп через файл + `--file-list` |
| Полнотекст по коду | ripgrep `--json` | stdout, построчный NDJSON |

Sidecar собирается лениво (`ensureBuiltRoslynIndexer`) и переиспользуется.

**Оценка: сильное решение.** Ключевое здесь — **парсинг C# через настоящий AST, а не регулярками**. Это то, на чём ломается 90% похожих самодельных индексаторов: regex не переживает вложенные типы, generic-констрейнты, `partial`, атрибуты. Использование Roslyn — правильный, «взрослый» выбор, и цена (зависимость от .NET SDK) оправдана.

Обмен через временный JSON-файл на диске вместо stdin/stdout — прагматично для многомегабайтных дампов, но это единственное место, где конвейер выглядит «файловым»: имя файла собирается как `${path}.${pid}.${Date.now()}.${random}.files.txt` — уникальность обеспечена, но очистка зависит от `finally`.

### 2.3. Реестр профилей игры (мультиверсионность как first-class)

**Где:** `utils/game-registry.ts`, `utils/game-profile-contract.ts`

Каждая версия игры — отдельный «профиль» в `dist/games/<base>-<version>/`. Ключевые решения:

- **`profile.json` как маркер готовности.** Пишется последним, после валидации индекса. Нет файла → профиль `broken`. Это классический *commit marker* / *success file* из мира data-инженерии (`_SUCCESS` в Hadoop/Spark).
- **`INDEX_SCHEMA_VERSION = 3` в контракте.** Профиль, собранный старым кодом, распознаётся как несовместимый вместо падения с SQL-ошибкой посреди запроса.
- **Живое сканирование при каждом вызове.** `listProfiles()` читает `dist/games/*` синхронно (`readdirSync`) — намеренно, потому что регистрация инструментов в `server.ts` происходит на синхронной загрузке модуля.
- **`profiles.json` — advisory-манифест.** Рецепты пересборки исчезнувших профилей; резолвер ему никогда не доверяет, только `list_game_versions` показывает их как `missing`.
- **Валидация консистентности:** суффикс каталога должен совпадать с `gameVersion` из контракта, `profileId` — с именем каталога, файл БД и каталоги `Source`/`Xmls` должны существовать.

**Оценка: это лучшая часть репозитория.** Многие MCP-серверы для игр/фреймворков просто предполагают одну установленную версию. Здесь мультиверсионность спроектирована как отдельная фаза (по коммитам видно: фазы 0-2, 3-5, 6-7), с явным контрактом и деградацией по одному профилю: один сломанный профиль не блокирует чтение остальных (`stdio.ts:23-38`).

### 2.4. Fail-fast резолюция версий вместо тихого фолбэка

**Где:** `utils/game-registry.ts:250-330`

Приоритетная матрица: явный `version` в вызове → `BANNERSAGE_DEFAULT_VERSION` → legacy `BANNERSAGE_GAME` → старший готовый версионированный профиль → legacy-профиль `bannerlord` → **жёсткая ошибка со списком доступного**.

Отдельно ценно: неоднозначность (две версии с одинаковой display-версией) **бросает исключение**, а не «выбирает первую». Неготовый профиль тоже даёт ошибку, а не откат к дефолту.

**Оценка: очень правильно.** Тихий фолбэк на другую версию игры — худший класс багов в такой системе: модель уверенно пишет патч под 1.3.15, читая сигнатуры из 1.5.1. Явная ошибка дешевле. Это применение принципа «errors should never pass silently» именно там, где он важен.

Единственный остающийся тихий сдвиг честно задокументирован в `AGENTS.md`: дефолт «старший готовый профиль» уплывает при индексации новой версии.

### 2.5. Явный контекст вместо ambient state (`GameContext`)

**Где:** `utils/game-context.ts`

```ts
export type GameContext = {
  gameId: string; gameVersion: string
  sandbox: PathSandbox; sourcePath: string
  db: () => Database
}
```

18 инструментов принимают `ctx` первым аргументом. Комментарий в коде формулирует мотив точно: «чтобы вложенный вызов никогда не мог тихо откатиться на активный профиль вместо того, который резолвил вызывающий».

**Оценка: эффективно и недооценённо.** Это ручной DI/reader-паттерн. Альтернатива (глобальный «текущий профиль» + AsyncLocalStorage) была бы либо хрупче, либо тяжелее. Здесь же тип-система физически не даёт написать инструмент, который читает не тот профиль. Плюс `versionEchoFields(ctx)` возвращает `game_id`/`game_version` в каждый ответ — модель всегда видит, из какой версии пришли данные. Это самодокументирующийся вывод, и он спасает от галлюцинаций про версии.

### 2.6. Атомарная публикация артефактов (staging → swap → trash)

**Где:** `utils/profile-publish.ts`

```
staging/<id>__<uuid>/   ← сборка идёт сюда
       ↓ publishStagedProfile()
1. mv dist/games/<id>  → .trash/<id>__<uuid>   (если был)
2. mv staging/<id>__…  → dist/games/<id>
3. rm -rf .trash/<id>__…
```

При старте `sweepStagingAndTrash()` восстанавливает состояние: staging-каталог = процесс умер в середине сборки → выбросить; trash-каталог при **пустом** целевом слоте → вернуть обратно; при занятом → выбросить как устаревший. Есть `renameWithRetry` с нарастающей паузой на `EPERM/EBUSY/EACCES` и принудительным `Bun.gc(true)` — прямое лечение Windows-специфики (антивирус/индексатор держит хэндл).

**Оценка: production-grade, редко встречающийся уровень для домашнего инструмента.** По сути это blue-green deployment для локальных данных. Единственный сценарий, который стоит держать в голове: между шагами 1 и 2 профиль отсутствует, и параллельно работающий MCP-сервер получит ошибку — но это честнее, чем читать полуразобранный индекс, и `getDb` держит открытый read-only хэндл, что на Windows скорее приведёт к retry-циклу, чем к порче.

Симметрично: обновление «на месте» (без staging) сначала **удаляет** `profile.json`, честно помечая профиль сломанным на время пересборки.

### 2.7. Инкрементальная сборка с fingerprint-кэшем

**Где:** `scripts/setup.ts:130-200`, `scripts/index-csharp.ts:100-160`, `scripts/index-xml.ts:1880-1965`

Трёхуровневая проверка «нужно ли пересобирать»:
1. `size + mtimeMs` совпали и выходной каталог непуст → пропуск (дёшево);
2. иначе — MD5 файла (`computeFileMd5`) → пропуск, если совпал;
3. иначе — декомпиляция.

То же для C#-индекса (`csharp_files` с `fileSize`/`fileMtimeMs`) и XML (`xml_files`). Плюс `mapWithConcurrency` с числом джобов от `availableParallelism()`.

**Оценка: эффективно.** Стандартный, но грамотно реализованный content-addressable кэш. Дешёвая проверка перед дорогой — правильный порядок. Отдельно хорошо, что при отсутствии инкрементальной схемы в БД (`hasIncrementalSchema`) код честно делает полный `resetCsharpSchema` вместо попытки мигрировать.

### 2.8. Инвалидация кэшей через revision-файл + наблюдатели

**Где:** `utils/runtime-revision.ts`, потребители — `utils/db.ts:52`, `utils/text-file-cache.ts:88`

`Version.txt` в каталоге профиля — маркер ревизии. Любое чтение вызывает `ensureRuntimeRevisionFresh(gameId)`; если строка изменилась с прошлого наблюдения — вызываются все зарегистрированные `registerRuntimeInvalidator`, которые закрывают SQLite-соединения и чистят кэш файлов.

**Оценка: изящно и уместно.** Это pull-based инвалидация вместо `fs.watch`: нет фонового вотчера, нет гонок при переименовании каталога, нет лишних дескрипторов. Стоимость — один `readFileSync` небольшого файла на вызов инструмента, что пренебрежимо на фоне SQLite-запроса. Observer-регистрация (`registerRuntimeInvalidator`) держит связность низкой: `runtime-revision` не знает про `db` и `text-file-cache`.

### 2.9. LRU-пулы ресурсов

**Где:** `utils/db.ts` (4 соединения), `utils/text-file-cache.ts` (8 файлов)

Соединения к SQLite открываются `{ create: false, readonly: true }` и кэшируются по пути с LRU-вытеснением. Кэш текстовых файлов валидируется по `mtimeMs + size` и хранит уже разбитые на строки массивы (что и нужно для срезов `read_file`/`read_csharp_type`).

**Оценка: эффективно, размеры выбраны разумно.** Комментарий в коде объясняет мотив: не переоткрывать 700-мегабайтный файл на каждый вызов при переключении версий. Держать `lines: string[]` в памяти для 8 файлов — приемлемый расход.

### 2.10. Гибридный поиск: FTS5 + ripgrep + B-tree

**Где:** `tools/search-xml.ts`, `tools/search-source.ts`, `scripts/index-xml.ts:437-449`

Три разных механизма под три разных запроса:

| Запрос | Механизм | Детали |
|---|---|---|
| «в каких XML упоминается X» | FTS5 + BM25 | `bm25(xml_documents_fts, 8.0, 4.0, 1.0)` — вес пути ×8, модуля ×4, содержимого ×1; `snippet()` для контекста |
| «где в коде встречается X» | ripgrep `--json` | префиксные токены не нужны, работает по живому дереву |
| «дай сущность по id» | B-tree индексы | `xml_entities_type_id_idx` и 8 предметных индексов |

`buildFtsQuery` превращает `"party speed"` в `"party"* AND "speed"*` — префиксный AND-поиск, разумный дефолт.

**Оценка: правильное разделение.** Взвешенный BM25 (путь важнее содержимого) — осмысленная настройка ранжирования, а не дефолт «из коробки». Использование ripgrep вместо FTS по коду тоже верно: код меняется реже, но запросы к нему чаще регексовые, а FTS5 регексы не умеет.

### 2.11. Материализованные предметные проекции

**Где:** `scripts/index-xml.ts:272-436`

Помимо универсальной `xml_entities` строятся денормализованные таблицы: `bannerlord_items`, `bannerlord_troops`, `bannerlord_heroes`, `bannerlord_cultures`, `bannerlord_skills`, `bannerlord_clans`, `bannerlord_kingdoms`, `bannerlord_settlements`. Инструменты вроде `get_item_stats` — это плоский `SELECT * WHERE entityId = ?`.

Поверх лежит `utils/bannerlord-entity-resolver.ts`, который разворачивает межссылочные `Culture.aserai` / `Faction.clan_x` в человекочитаемые имена, а `utils/localization.ts` резолвит токены `{=abc123}` в реальный текст.

**Оценка: эффективно.** Схема «сырое хранилище + предметные проекции» — то, что позволяет держать инструменты тонкими. Резолюция ссылок и локализации **на стороне сервера, а не модели** — важное решение: иначе агент тратил бы 3-4 лишних вызова на каждый ответ.

### 2.12. Токен-ориентированный формат вывода

**Где:** `utils/ai-text.ts`

Собственный плоский формат вместо JSON:

```
report_type: item_stats
query_item_id: saddle_horse
result_count: 1
game_id: bannerlord-1.5.1
game_version: 1.5.1

[result_1]
result_label: Item_1
weight: 30
...
```

Плюс жёсткие лимиты: `MAX_MATCH_RESULTS = 200`, `MAX_TYPE_MATCHES = 5`, `MAX_LINES_THRESHOLD = 400`, `LIMIT 10` в FTS-поиске, и явные поля `truncated` / `total_matches_found` / `match_limit`, чтобы модель понимала, что видит не всё.

Отдельная находка — `summarizeTypeSurface` (`utils/csharp-type-reader.ts:113-144`): типы длиннее 400 строк отдаются как «поверхность» (сигнатуры) с телами, свёрнутыми в `// ... implementation hidden ...`, через простой счётчик глубины скобок с вырезанием строк и комментариев.

**Оценка: очень актуально для 2026, с одной оговоркой.** Context-budget engineering сейчас — основной рычаг качества агентных инструментов, и здесь он проработан лучше, чем в большинстве MCP-серверов: экономия относительно эквивалентного JSON примерно 30-40%, а сворачивание тел методов бьёт ровно в главный источник раздувания.

Оговорка: формат самодельный и не имеет экранирования. Скалярное значение с переносом строки, попавшее в `fields` (а не в `multilineFields`), сломает построчную структуру. Сейчас это не проявляется, потому что вызывающие аккуратны, но контракт держится на дисциплине, а не на коде.

### 2.13. Прогрессивное раскрытие инструментов (toolset gating)

**Где:** `utils/bannerlord-toolset.ts`, `entrypoints/*.ts`

Два entrypoint-а — тонкие обёртки, которые выставляют `BANNERSAGE_TOOLSET` и динамически импортируют `stdio.ts`:

```ts
process.env.BANNERSAGE_GAME ||= 'bannerlord'
process.env.BANNERSAGE_TOOLSET ||= 'query-first'
const { main } = await import('../stdio')
```

Режим `query-first` даёт 29 инструментов, `full` — 30 (добавляется `generate_xslt_patch`).

**Оценка: механизм правильный, применение — почти вхолостую.** Идея гейтинга здравая, но разница в один инструмент из тридцати не решает проблему, ради которой такие механизмы вводят. Подробнее — в разделе 4.

Отдельно замечу мелкую несогласованность: `getBannerlordToolsetMode()` при пустом env возвращает `'full'`, тогда как оба Bannerlord-entrypoint-а выставляют `query-first`. Прямой запуск `src/stdio.ts` даст режим, отличный от документированного дефолта.

### 2.14. Инструменты как промпт (tool descriptions as prompt engineering)

**Где:** `server.ts`

Описания написаны в форме «когда это применять», а не «что это делает»:

> «Use this when you do not yet know the exact type or method location… best for hunting symbols, comments, string literals… **before** drilling into a specific file or type.»

> «Prefer this over broad text search for classes, structs… because it jumps straight to the indexed declaration.»

Плюс динамическая генерация: `buildVersionParamDescription()` вшивает в описание параметра `version` актуальный список проиндексированных версий и текущий дефолт. Комментарий честно объясняет, почему это безопасно замораживать на старте: `resolveGameId()` всё равно пересканирует живьём, поэтому устаревшая подсказка может лишь ухудшить догадку модели, но не привести к тихому чтению не той версии.

Все инструменты помечены аннотациями `readOnlyHint` / `openWorldHint`.

**Оценка: соответствует лучшим практикам 2026.** Описания с явным «prefer X over Y» и указанием порядка вызовов — это то, что реально снижает количество бесполезных вызовов. Аннотации по спеке проставлены корректно (`project_memory_*` на запись честно помечены `readOnlyHint: false`).

### 2.15. Отдельный слой проектной памяти

**Где:** `utils/memory-db.ts`, `utils/project-memory.ts` (645 строк), 6 инструментов

Своя writable SQLite (`<base>-memory.db`), **общая для всех версий одной игры** (`env.ts:memoryDbPath` резолвится через `resolveBaseProfileId`). Схема: `project_memories` + FTS5 `project_memories_fts`.

Ключевые решения:
- **Взвешенный BM25 с приоритетами полей:** `bm25(project_memories_fts, 0.2, 1.0, 1.0, 1.0, 2.0, 0.5)` — `summary` весит ×2, `public_id` практически исключён;
- ранжирование `ORDER BY rank ASC, importance DESC, updated_at DESC` — семантика поверх релевантности;
- **soft-delete вместо удаления:** `status = 'invalidated'` + `invalidation_reason` + `invalidated_at`. Инструмент называется `project_memory_invalidate`, а не `delete`;
- `project_memory_capture_session` — батч-запись в конце задачи вместо серии одиночных вставок, с разными дефолтными `importance` по категориям (decision=5, pitfall/preference/todo=4, note=3);
- `project_memory_wakeup` — загрузка «важного активного» в начале сессии.

**Оценка: продуманно, дисциплина вынесена в правильное место — но не в протокол.** Идея «память не версионируется вместе с индексом» верна: решение о том, как патчить кланы, переживает обновление игры. Soft-delete с причиной — правильно: «почему мы отказались от подхода» само по себе ценная память.

Два наблюдения:
- **Синхронизация FTS ручная.** `project_memories_fts` — обычная FTS5-таблица, а не external-content с триггерами. Вставки в основную таблицу и в FTS делаются рядом в коде. Работает, но рассинхрон возможен при любой новой точке записи. External content + `AFTER INSERT/UPDATE/DELETE` триггеры дали бы гарантию на уровне БД и заодно сэкономили место.
- **Поиск чисто лексический.** На середину 2026 гибрид BM25 + эмбеддинги — норма для памяти агентов; здесь нет векторов, и запрос «как мы решали проблему с производительностью» не найдёт память, где написано «тормозит на тике кампании». Но это осознанный компромисс: эмбеддинги ломают offline-first (нужна модель или API). Учитывая приоритеты проекта — защитимо; `sqlite-vec` с локальной моделью был бы вариантом, если приоритеты сдвинутся.

### 2.16. Ленивая переиндексация мод-исходников (read-through cache)

**Где:** `utils/local-mod-csharp-index.ts`

Все три мод-инструмента (`mod_source_status`, `index_mod_source`, `read_mod_type`) начинаются с `ensureLocalModSourceIndex(workspaceRoot)`, который инкрементально переиндексирует только изменённые файлы.

**Оценка: правильный компромисс.** Мод-исходники, в отличие от игры, меняются постоянно — сотни раз за сессию. Read-through с инкрементальностью снимает с пользователя обязанность помнить про переиндексацию, а стоимость «ничего не изменилось» близка к нулю (обход дерева + сравнение mtime).

### 2.17. Песочница путей и read-only доступ

**Где:** `utils/path-sandbox.ts`, `utils/db.ts:24`

`PathSandbox` резолвит путь относительно корня `assets` и отвергает всё, что уходит за него (`relative().startsWith('..')`). Все игровые БД открываются `readonly: true, create: false`.

**Оценка: базовая защита есть, но реализация упрощённая.** Для локального доверенного дерева достаточно, однако:
- нет `realpath` — символическая ссылка внутри `assets`, указывающая наружу, проверку пройдёт;
- проверка `startsWith('..')` не отличает `..` от каталога с именем, начинающимся на `..` (редкий, но валидный случай) — надёжнее сравнивать сегменты пути;
- на Windows не учитывается регистронезависимость.

Модель угроз здесь мягкая (пути приходят от LLM, а не от злоумышленника), так что это не дыра, а недоделанный примитив. Если сервер когда-нибудь получит HTTP-транспорт — станет реальной проблемой.

### 2.18. Профили игр как стратегия

**Где:** `utils/game-profiles.ts` (637 строк), интерфейс `GameProfile`

Интерфейс с 9 методами (`detectGameDir`, `collectDllCandidates`, `collectXmlFiles`, `scoreDllPath`, …) и константами `requiresSource`/`requiresXml`/`requiresDb`. Внутри — довольно тонкая доменная логика: классификация модулей на официальные/сторонние по `SubModule.xml` + whitelist ID, четыре уровня `dllScope` (`core`/`modding`/`official`/`all`), denylist для нативных DLL, скоринг для приоритизации.

**Оценка: паттерн уместен, но сейчас работает вхолостую — и это нормально.** Профиль ровно один (наследие RimSage, из которого проект выведен). Абстракция стоит недорого и она уже окупилась внутри Bannerlord — уровни `dllScope` позволяют пользователю выбирать между «быстро и по делу» и «всё подряд», а классификация официальных модулей защищает от индексации чужих модов вместе с игрой. Стратегия здесь скорее для *конфигураций* одной игры, чем для разных игр, и в этом качестве она себя оправдывает.

### 2.19. Верификация скриптами вместо юнит-тестов

**Где:** `scripts/verify-versions.ts` (778 строк), `verify-bannerlord.ts`, `verify-project-memory.ts`, `smoke-release.ts`

`verify:versions` — фактически контрактный e2e-набор: проверяет, что все 18 версионных инструментов самодостаточны (нет неявной резолюции), что эхо-поля версий совпадают с профилем, параллельные чтения из разных профилей не смешиваются, сломанный профиль не создаёт БД, дублирующиеся display-версии отвергаются, память не версионируется. Тесты, требующие двух версий, честно деградируют до одно-профильной проверки и сообщают об этом.

`smoke:release` — прогон CLI-путей с проверкой ожидаемого текста в выводе.

**Оценка: содержательные проверки, но неправильный уровень.** Сами инварианты выбраны отлично — они бьют ровно в те места, где мультиверсионность может сломаться незаметно. Проблема в том, что запустить их можно только имея установленную игру и собранный многогигабайтный индекс. Подробнее — раздел 4.

## 4. Что отстаёт от современного baseline

Расположено по убыванию значимости.

### 4.1. Нет structured output (`outputSchema` / `structuredContent`) — главное отставание

Спецификация MCP начиная с ревизии 2025-06-18 позволяет инструменту объявить `outputSchema` и вернуть `structuredContent` рядом с текстом. Здесь **все 30 инструментов возвращают только `content: [{ type: 'text' }]`**.

Самодельный `ai-text` формат хорош для токенов, но:
- клиент не может валидировать ответ;
- программный потребитель (не-LLM) вынужден парсить формат без спецификации;
- теряется машинная типизация там, где данные строго структурны (`get_item_stats` — это ровно набор числовых полей).

**Что делать:** отдавать оба. `content` остаётся токен-экономным текстом для модели, `structuredContent` + `outputSchema` (Zod уже в зависимостях, схемы выводятся из него) — для клиента. Изменение аддитивное и обратно совместимое.

### 4.2. Тридцать инструментов в одном сервере, а гейтинг не используется

30 определений инструментов с подробными описаниями — это заметный постоянный расход контекста в каждом запросе клиента, ещё до первого полезного действия. Механизм `query-first` / `full` существует, но отсекает **один** инструмент.

К середине 2026 стандартный ответ на это — прогрессивное раскрытие: отложенные определения с поиском по инструментам (так работает `ToolSearch` в самом Claude Code), группировка по неймспейсам, или meta-tool-фасады.

**Что делать (по возрастанию усилий):**
- сгруппировать 10 gameplay-lookup-ов в один `get_gameplay_entity(kind, id)` с дискриминированным union — минус 9 инструментов почти без потери удобства;
- вынести 6 инструментов памяти в отдельный сервер или за флаг — они ортогональны Bannerlord и полезны сами по себе;
- сделать `query-first` действительно узким (7-10 инструментов), с догрузкой остальных по требованию.

### 4.3. Нет автоматических тестов на чистые функции

`bun test` доступен бесплатно, а в коде есть готовый к тестированию слой чистой логики, где ошибка стоит дорого и незаметна:

| Функция | Почему важна |
|---|---|
| `compareGameVersions`, `parseVersionComponents` | определяет, какая версия «старшая» → какой профиль дефолтный |
| `matchProfileAlias` | вся приоритетная матрица резолюции, включая бросок при неоднозначности |
| `buildFtsQuery` | корректность экранирования пользовательского ввода в FTS5 |
| `summarizeTypeSurface` | счётчик скобок с вырезанием строк/комментариев — классический источник краевых случаев |
| `PathSandbox.validateAndResolve` | граница безопасности |
| `parseLocalizationToken`, `normalizeReference` | парсинг доменных форматов |
| `renderAiTextReport` | контракт выходного формата |

Сейчас все они покрыты только опосредованно — через `verify:*`, которым нужна установленная игра и собранный индекс. То есть регрессия в `compareGameVersions` обнаружится не на CI, а у пользователя.

**Это самая дешёвая точка улучшения во всём репозитории:** десяток файлов `*.test.ts`, ноль новых зависимостей, ноль требований к окружению, и они закроют логику, которую сейчас страхует только внимательность.

### 4.4. Нет MCP Resources и Prompts

Протокол даёт три примитива, используется один.

- **Resources.** `list_directory` / `read_file` — это буквально ResourceTemplates (`bannerlord://{version}/assets/{path}`). Через Resources клиент может показать дерево, дать пользователю выбрать файл вручную, кэшировать и подписаться на обновления — сейчас всё это невозможно.
- **Prompts.** В `AGENTS.md` лежит подробный воркфлоу проектной памяти («в начале задачи вызови `wakeup`, перед ответом о прошлых решениях — `search`, в конце — `capture_session`»). Это идеальный кандидат на MCP Prompt. Сейчас правила живут **вне протокола**: клиент, который не читает `AGENTS.md`, их не получит, и вся дисциплина памяти держится на том, что пользователь заранее скормил агенту нужный файл.

### 4.5. Нет progress-нотификаций и отмены для долгих операций

`index_mod_source` на большом воркспейсе может работать минуты (обход дерева, запуск Roslyn, вставки в SQLite). Клиент всё это время видит зависший вызов. MCP поддерживает `notifications/progress` с токеном и отмену — не используется.

### 4.6. Только stdio-транспорт

Streamable HTTP в SDK 1.26 есть; здесь только `StdioServerTransport`. Следствия: нет удалённого доступа, нет нескольких одновременных клиентов, нет OAuth.

**Это скорее осознанный выбор, чем недостаток.** Сервер по определению работает с локальной установкой игры на 60+ ГБ; смысл в удалённом доступе к нему невелик, а stdio исключает целый класс проблем с аутентификацией. Но стоит зафиксировать как ограничение: масштабирование на «команду модеров с общим индексом» потребует переписывания транспортного слоя, и вот тогда упрощения в `PathSandbox` (п. 2.17) станут значимыми.

### 4.7. `db.query<any, any>` — потерянная типизация в read path

Большинство gameplay-инструментов запрашивают строки как `any`:

```ts
const rows = db.query<any, any>(`SELECT * FROM bannerlord_items WHERE entityId = $id`).all({ $id: itemId })
```

Затем `row.swingDamage`, `row.balanceOrHitPoints` и ещё два десятка полей читаются без всякой проверки. Схема при этом **известна статически** — она объявлена в `scripts/index-xml.ts`. Переименование колонки в индексаторе не вызовет ни одной ошибки компиляции, а проявится как `unknown` в выводе для пользователя.

**Что делать:** объявить row-типы рядом со схемой (`type BannerlordItemRow = {...}`) и экспортировать их для инструментов; `SELECT *` заменить на явный список колонок. `csharp-type-reader.ts` уже делает правильно (`db.query<CSharpTypeMatchRow, {$name: string}>`) — достаточно распространить этот стиль.

### 4.8. Глобальный синглтон `server` на загрузке модуля

`server.ts` создаёт `export const server = new McpServer(...)` и регистрирует все инструменты как побочный эффект импорта; `env.ts` вычисляет `activeGameId`/`activeGamePaths` тоже на импорте. Для однопроцессного stdio-сервера это работает, но делает модуль нетестируемым: нельзя создать два сервера с разными env в одном процессе, нельзя импортировать `server.ts` без запуска регистрации.

**Что делать:** обернуть в `createServer(config)`, оставив синглтон только в `stdio.ts`. Это заодно откроет дорогу к интеграционным тестам через `InMemoryTransport` из SDK.

### 4.9. Отсутствие миграций схемы

`INDEX_SCHEMA_VERSION` даёт корректное обнаружение несовместимости, но единственный путь восстановления — полная пересборка, а она включает декомпиляцию (десятки минут). Для аддитивных изменений (новая колонка, новая таблица проекции) `ALTER TABLE` + бамп минорной версии сэкономил бы пользователю час на ровном месте. Учитывая, что индекс — производные данные, приоритет невысокий, но при частых изменениях схемы это станет заметно.

### 4.10. Привязка к Bun

`bun:sqlite`, `Bun.spawn`, `Bun.gc`, `import.meta.main` — сервер не запустится на Node. На середину 2026 Bun — зрелый рантайм, и выигрыш реален (встроенный SQLite без нативной сборки — большое удобство на Windows), так что это защитимый выбор. Но он сужает аудиторию: пользователь обязан ставить Bun, .NET SDK, ILSpyCmd и ripgrep до того, как что-либо заработает. Четыре внешние зависимости — высокий порог входа для модерского инструмента.

## 5. Итоговая оценка

**Сильная сторона — операционная зрелость.** Атомарная публикация с восстановлением после сбоя, контракт профиля с версией схемы и маркером готовности, деградация по одному профилю, инкрементальные сборки с fingerprint-кэшем, fail-fast вместо тихого фолбэка — это уровень, характерный для внутренних data-платформ, а не для утилиты вокруг игрового моддинга. Мультиверсионность (коммиты `fe8a503` → `b5eaa0b`) сделана по фазам, с явными инвариантами и отдельным набором регрессионных проверок под них.

**Вторая сильная сторона — понимание того, что потребитель API это LLM.** Лимиты результатов с явным флагом `truncated`, сворачивание тел методов у больших типов, эхо `game_id`/`game_version` в каждом ответе, серверная резолюция ссылок и локализации, описания инструментов в форме «когда применять вместо чего». Это не общие слова про «AI-friendly», а конкретные решения, каждое из которых экономит либо токены, либо ошибочный вызов.

**Основной разрыв с baseline середины 2026 — на границе протокола, не внутри логики.** Внутренняя архитектура здорова; недостаёт того, что MCP уже предлагает и что клиенты уже умеют потреблять: structured output, Resources, Prompts, progress-нотификации. Плюс два «инженерных долга», не связанных с MCP: отсутствие юнит-тестов на чистую логику и `any`-типизация в read path.

**Приоритетный порядок работ, если он нужен:**

1. **Юнит-тесты на чистые функции** (`compareGameVersions`, `matchProfileAlias`, `buildFtsQuery`, `PathSandbox`, `summarizeTypeSurface`) — максимальная отдача на вложенные усилия, ноль новых зависимостей и требований к окружению.
2. **`outputSchema` + `structuredContent`** аддитивно ко всем инструментам — приводит сервер к текущему уровню спеки, ничего не ломая.
3. **Сокращение поверхности инструментов** — объединить 10 gameplay-lookup-ов в один параметризованный, вынести память за отдельный флаг или в отдельный сервер.
4. **Row-типы вместо `db.query<any, any>`** — объявить рядом со схемой в `index-xml.ts`, убрать `SELECT *`.
5. **MCP Prompt для воркфлоу памяти** — перенести правила из `AGENTS.md` в протокол, чтобы они работали независимо от клиента.
6. **FTS5 external-content + триггеры** для `project_memories` — гарантия синхронизации на уровне БД вместо дисциплины в коде.
